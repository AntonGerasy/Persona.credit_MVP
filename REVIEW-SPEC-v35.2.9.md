**Это последняя спецификация перед PB1.** Четыре класса, закрытый список, критерий приёмки жёсткий. После неё я даю GO или NO-GO и новых классов не ищу.

## Универсальное правило (формулировка принята без изменений)

> Extraction reliability must be institution-, country-, language-, format- and document-length agnostic. Any accepted document that exceeds safe single-pass extraction capacity must automatically use chunked extraction. A processing failure of any supplied evidence must never be converted into missing evidence, an authenticity concern, or an adverse financial signal.

Ни одной ветки по названию банка, страны или языка. Решение о чанкинге принимается по характеристикам самого файла.

> **Для любого принятого документа существуют ровно два исхода: COMPLETE или RETRY. Никогда PARTIAL.**

## C021 — сбой с кодом 200 невидим для C019 · P0

`api/extract-document.ts:827` возвращает HTTP 200 с заглушкой; клиент (`App.tsx:982`) регистрирует только не-200. Гард C019 сигнала не получает.

1. В fallback-объект добавить `processing_failed: true`.
2. Клиент после `response.json()`: при `parsed.processing_failed === true` — в `extractionFailures` с `kind: 'server'`, документ **не** добавлять в `extractedDocuments`.
3. Дальше отрабатывает существующий C019 → Retry-экран, скор не создаётся.

## C022 — техническая ошибка не является сомнением в подлинности · P0

`api/extract-document.ts:851` пишет текст исключения в `authenticity_concerns`. В отчёте это вышло как «Authenticity concerns for two Ukrainian documents» о подлинном документе с ЭЦП.

Убрать. Для диагностики есть `rejection_reason` и `analyst_note`. Инвариант: **ни один технический сбой ни при каких условиях не попадает в поля, которые читаются как суждение о человеке или его документе.**

## C023 — маркер self-transfer обходит многосигнальную защиту · P1

`api/extract-document.ts:381` — первая ветвь, короткое замыкание. Строка `Online transfer from CHK 1632 ... CODECTIVE INC` совпала с `transfer from chk` и `online transfer from`. При этом `employerRelated`, `recurringPayer` и `similarRecurringAmounts` уже посчитаны выше (комментарий на строке 356 прямо объясняет зачем) — но используются только в ветке `else`.

При совпадении маркера self-transfer: если в counterparty присутствует именованное юрлицо (совпадение с `employerTokens` либо суффикс INC/LLC/LTD/GMBH/ТОВ/ПП и подобные, не совпадающий с `applicantTokens`) — направлять в `reviewRequired`, не в `excluded`. Порядок ветвей не менять, достаточно условия внутри первой.

## C024 — Universal Long-Document Extraction · P0

Причина: промпт допускает до 240 записей, `maxOutputTokens: 14000` их не вмещает. На реальном документе (15 страниц, 359 транзакций, кириллица) ожидаемый ответ ~27 000 токенов → обрыв → `JSON.parse` → заглушка.

### Архитектура

**Чанкуем всегда**, окном в N страниц. Одностраничный документ — один чанк. Порога «длинный/короткий» не существует, значит нечему ошибаться.

**Оркестрация на клиенте.** `maxDuration: 60` на Hobby — потолок платформы; пять последовательных вызовов Vision в него не поместятся. Эндпоинт принимает `pageRange` и возвращает часть; клиент вызывает его N раз и собирает результат детерминированно. Функция остаётся короткой, пользователь видит прогресс.

Пересчитать лимит `extract-document` в `requireAiSession` (сейчас 30/мин): три документа по пять чанков — это 15 вызовов за прогон.

**Изображения.** Одиночная картинка — сам по себе один чанк, отказывать по типу файла нельзя. C021 применяется, только если извлечение действительно не удалось. Существующая отсечка 5 МБ остаётся.

`maxOutputTokens` поднять как запас, но не как основной фикс.

### Сборка — два инварианта

**Никакой content-based дедупликации.** Две идентичные транзакции — это две записи, пока не доказано обратное. Дедупликация допустима только внутри полосы перекрытия соседних чанков и только по позиции строки. При нарезке строго по страницам не нужна вообще.

**Реконсиляция контрольных величин.** Выписки почти всегда печатают опорные числа: monobank — «Баланс на початок/кінець періоду», «Сума зарахувань/витрат за період»; BoA — Beginning/Ending balance, Total deposits/withdrawals. Проверка арифметическая:

```
начальный баланс + Σ кредитов − Σ дебетов ≈ конечный баланс
```

Не сходится в допуске → `processing_failed: true` → C021. Ловит обрыв чанка, пропущенную страницу и галлюцинированные суммы одновременно. Контрольных величин в документе нет → проверка **неприменима**, а не провалена. Просить модель извлекать эти четыре числа отдельным полем в каждом чанке (печатаются в шапке, попадут в первый).

## Тесты

Разделение обязательно, иначе CI пойдёт в Gemini.

**Блокирующие в `test:pb1`** — на синтетических payload'ах чанков (JSON), без сети:
1. склейка N чанков сохраняет все записи, включая шесть идентичных и две неразличимые до отметки времени;
2. склейка с недостачей → реконсиляция не сходится → `processing_failed`;
3. один чанк из пяти с ошибкой → весь документ `processing_failed`, ассессмент заблокирован;
4. документ без контрольных величин → проверка не выполняется, документ не считается провалившимся;
5. одностраничный документ → один чанк, поведение не изменилось;
6. ответ 200 с `processing_failed: true` → `allowFinancialVerdict: false` (кейс C021, сейчас его в сьюте нет);
7. кредит с маркером `transfer from chk` + названное юрлицо → `review_required`; тот же маркер без юрлица → `excluded` (C023).

**Живая проверка** — вручную при `PERSONA_QA_FIXTURE_MODE=true` на фикстуре P8 (12 страниц, 698 транзакций, кириллица, все четыре ловушки, контрольные величины сходятся до нуля). Файл и генератор в `qa-personas/`.

## Критерий приёмки

Те же самые реальные файлы, что выявили дефект. Допустимы ровно два исхода:

**A — COMPLETE.** Оба документа извлечены, украинский появляется нормальным Evidence Node, `UNKNOWN — UNKNOWN` отсутствует, суммы кредитов и дебетов в отчёте **сходятся с контрольными числами из шапки выписки**. Без этой сверки «извлечён» проверяется на глаз.

**B — RETRY.** Что-то не обработалось → Processing Incomplete → TransferScore не создаётся, adverse narrative отсутствует, обвинений в неподлинности нет, отчёт не персистится.

Исход «часть потерялась, но мы посчитали 384» существовать не должен.
