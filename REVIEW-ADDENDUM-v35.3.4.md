## 1. Добавить в правку №2: делитель периода, а не только подпись

Гард из ТЗ (`04/27/26 + 05/01/26 ⇒ Apr–May 2026`) проверяет подпись периода, но не число месяцев. А число месяцев ломается ровно тем же исправлением: как только даты читаются верно, выписка с 14 апреля по 11 мая перестаёт быть «одним месяцем» и становится **двумя календарными** — и обязательства делятся на два.

Проверено на реальных строках из этого прогона BoA:

```
только правка дат:        период 2 месяца → obligations 609/мес
правка дат + делитель:    период 1 месяц  → obligations 1 218/мес   ← факт документа
```

Это не новое улучшение и не расширение списка: без этого правка №2 меняет одну неверную цифру («2026-01») на другую («÷2»). Американские и британские выписки почти всегда пересекают границу месяца, так что это системная ошибка ровно на целевом рынке.

**Правка в `deriveReliablePeriod`,** вместо `const calendarMonths = Math.min(36, Math.max(1, maxIdx - minIdx + 1));`:

```ts
// Calendar-month counting overstates a statement that merely straddles a month boundary
// (14 Apr - 11 May is one month of activity, not two). Measure the actual dated span.
const windowDates = parsed.filter((d) => {
  const idx = d.getUTCFullYear() * 12 + d.getUTCMonth();
  return idx >= minIdx && idx <= maxIdx;
});
const spanDays = (Math.max(...windowDates.map((d) => d.getTime())) - Math.min(...windowDates.map((d) => d.getTime()))) / 86400000;
const calendarMonths = Math.min(36, Math.max(1, Math.round(spanDays / 30.44)));
```

Проверено: BoA → 1 месяц и 1 218/мес; украинская выписка → 6 месяцев и доход 31 344 (не изменилось); гард на выброс года и все 23 smoke-проверки зелёные.

Заодно подпись: сейчас получится «1 calendar months». Заменить на `(${reliablePeriod.months} month(s) of activity; transaction-derived)`.

## 2. Снимаю свою прошлую правку про contradiction

В прошлом заключении я требовал третью правку: запретить статус `contradicted`, пока в аудите есть кредиты в review. **Снимаю — GPT прав, симптом уйдёт сам, и я могу показать, по какой именно ветке.**

`src/App.tsx:1084` определяет полноту чтения так: для банковской выписки `complete` возможен **только** если напечатаны все четыре контрольные суммы и транскрипт сходится с ними в пределах 1%. По вашему же эталону расходы в украинской выписке недобраны на 5 682,95 из 216 042,90 — это 2,6%, больше допуска. Значит документ получит `partial`, `financialEvidenceIncomplete` станет `true`, и существующий код на строке 1685 выставит `incomeStatus = 'partial'` **раньше**, чем дойдёт до ветки `contradicted`, а на 1793 обнулит contradiction_score.

То есть `−20` действительно исчезнет без единой новой строки. Более того, для чанкованных выписок ветка `contradicted` в текущей архитектуре почти недостижима вообще.

В бэклог, не в работу: путь одиночного изображения (`App.tsx:1128`) ставит `complete` безусловно — там противоречие теоретически возможно. Условие для будущего правила формулирую заранее, чтобы не искать заново: *статус `contradicted` не выставляется, пока в income-аудите есть строки `review_required`.*

## 3. Две ловушки реализации правки №1

Обе стоили бы вам лишнего прогона.

**Порядок.** Правило пригодности должно стоять **после** обоих движков, но к этому моменту `result.credit_transactions` и `result.debit_transactions` уже удалены (`delete` сразу после каждого движка). Проверять надо не массивы, а аудит:

```ts
const hasDeterministicTranscript =
  result.income_audit?.engine === 'deterministic' || result.obligations_audit?.engine === 'deterministic';
```

**Отказ.** Вместе с `is_usable` надо гасить `rejection_reason`, иначе документ станет пригодным, но в отчёте останется висеть причина отказа, написанная моделью.

Рабочая формулировка, которую я прогнал:

```ts
const isBankStatement = /bank|statement|виписк|выписк|estado de cuenta|extrato|releve|kontoauszug/i
  .test(`${result.document_type || ''} ${result.issuing_institution || ''}`);
if (isBankStatement && hasDeterministicTranscript
    && result.processing_failed !== true && result.extraction_completeness !== 'unreadable') {
  result.is_usable = true;
  if (result.rejection_reason) result.rejection_reason = '';
}
```

Ни суммы, ни регулярности, ни плательщика, ни страны, ни валюты в условии нет — как и записано в ТЗ.

## 4. Про правку №2: три места закрываются одной переменной

ТЗ требует применить один и тот же порядок в `deriveReliablePeriod`, в группировке месяцев дохода и в группировке месяцев обязательств. Все три места вызывают один и тот же `parseTxDate`, поэтому **протаскивать параметр через три сигнатуры не нужно** — достаточно модульной переменной, выставляемой один раз в начале `finalizeExtractionResult`:

```ts
let numericDateOrder: 'day_first' | 'month_first' = 'day_first';
```

`finalizeExtractionResult` синхронна целиком, `await` внутри нет, поэтому два документа не могут перемешаться. Меньше правок — меньше риска, и требование «один порядок на документ» выполняется автоматически.

Внутри `parseTxDate` порядок сначала определяется по самой строке, и только для двусмысленных строк берётся документный:

```ts
if (a > 12 && b <= 12) return mkDate(fixYear(m[3]), b, a); // day-first proven
if (b > 12 && a <= 12) return mkDate(fixYear(m[3]), a, b); // month-first proven
return numericDateOrder === 'month_first' ? mkDate(fixYear(m[3]), a, b) : mkDate(fixYear(m[3]), b, a);
```

Оба гарда из ТЗ на этом проходят: `04/27/26 + 05/01/26` → апрель–май 2026; `27/04/26 + 01/05/26` → апрель–май 2026.
